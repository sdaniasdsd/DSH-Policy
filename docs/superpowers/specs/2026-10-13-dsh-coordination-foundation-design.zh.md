# DSH 协作基础能力与策略职责设计

[English](2026-10-13-dsh-coordination-foundation-design.md) | 中文

## 摘要

本说明描述 DSH 为策略提供的协作基础能力，以及 Superpowers 如何使用这些能力运行黑板流程。目标是在执行中遇到计划外问题时，策略仍能获得反馈、调整安排并继续已有会话。本文是待审阅的设计，不表示下述能力已全部接入策略运行路径。

用户已明确：Superpowers 使用黑板方式；Codex、Claude、ZCode 保留各自的协作方式；DSH 提供消息通道等基础能力。本文不设定风险数量、会议周期或新的权限规则。

## 职责划分

DSH 负责承载会话、控制执行、传递消息和保存共享记录。策略负责规划、分工、解释问题、调整计划、检查结果和判断完成。运行基础设施不能根据一条消息或一次工具失败自行推导业务裁决。

本文的策略主 agent（智能体）是对该任务作出规划和调整的决策会话。它与 DSH 的同步阶段选择函数不同。与用户对话的入口会话可以报告进展，但不能仅因为它位于最外层就假定它承担了策略裁决；策略接入时必须明确决策会话的身份及消息路由。

| 层次 | 职责 | 示例 |
|---|---|---|
| DSH 基础服务 | 提供会话、成员、消息、记录、等待和执行反馈 | 向指定成员投递消息并返回接收结果 |
| 策略适配器 | 将基础能力绑定到当前策略及其后端 | 将继续请求交给可继续的 DSH 会话或原生后端 |
| 策略流程 | 决定何时、为何使用这些能力 | Superpowers 根据黑板问题发起讨论 |

<a id="approach"></a>

## 方案选择

推荐复用现有会话和团队服务，以适配器接入不同策略，再由 Superpowers 实现黑板流程。这样可以沿用现有成员身份、消息接收与资源清理规则，并单独处理当前策略路径缺少的衔接。

统一由 DSH 调度所有策略也能形成一致流程，但会改变其他策略的协作方式。让每个策略独立实现通信和存储则会重复已有基础设施，并使恢复与通知语义分散。推荐方案保留基础能力的统一实现和策略流程的独立性。

<a id="foundation-capabilities"></a>

## 基础能力

基础能力以可观察的执行和状态为中心。以下是拟提供给策略的能力描述，不是已经发布的方法名称或类型声明。

| 能力 | DSH 提供的操作与结果 | 策略负责的选择 |
|---|---|---|
| 会话延续 | 引用独立会话、保存历史、继续已有会话、报告无法恢复 | 哪个成员需要继续、补充哪些上下文 |
| 成员生命周期 | 创建成员、查询状态、等待结果、中断当前执行、结束并清理 | 分工、并行安排、重新执行或替换成员 |
| 消息通道 | 按成员身份发送消息、接收通知、观察投递失败 | 收件人、内容、优先级及收到后的动作 |
| 共享记录 | 按任务读取与写入记录、观察版本及变更 | 记录的业务含义与采用方式 |
| 执行反馈 | 返回工具结果、错误、产物、验证证据及取消状态 | 如何恢复、是否验收通过 |
| 等待与唤醒 | 等待成员或记录变化、超时返回、按策略请求唤醒 | 检查时机、讨论时机及周期 |

消息通道保留真实发送者身份。接收成功表示消息被目标接收机制接受，不表示模型已经理解或执行消息。策略需要成员回报时，由策略规定回报内容；基础设施传递并保存该回报。

共享记录具有任务归属和版本。记录读取、消息投递、执行状态各自有明确结果；后台状态变化不会自动成为所有成员的上下文。策略需要通过读取记录、发送摘要或继续会话，把有关信息交给目标成员。

等待和周期唤醒由活跃任务拥有，任务取消或结束时释放相应运行资源。持久记录可以保留，但保存记录与恢复执行是两种能力；能重建历史不能单独证明能继续原来的后端会话。

<a id="current-source-and-integration-gaps"></a>

## 现有源码与衔接问题

本节是对当前工作区源码的静态观察。运行时集成和原生后端能力仍需要单独验证。

| 源码 | 静态观察 | 对本设计的影响 |
|---|---|---|
| [agent-team](../../../packages/experimental/agent-team/src/index.ts) | 提供成员创建、消息、共享任务、版本更新和变化等待 | 优先复用其基础机制；共享任务表不能直接等同于议题和决策黑板 |
| [subagent](../../../packages/subagent/subagent/src/index.ts) | 提供相邻会话通信和可继续子会话；继续依赖可用服务及授权关系 | 接入时需要保留可继续会话身份，并满足路由条件 |
| [dsh-child](../../../packages/experimental/task-strategy/src/dsh-child.ts) | 当前步骤等待结果后执行 dispose（资源释放） | 不能把这条步骤执行路径直接视为持续协作会话 |
| [TaskRun](../../../packages/experimental/task-strategy/src/task-run.ts) | 步骤执行结果不是 completed 时，运行进入终态 | 当前路径不能仅靠下一次阶段选择处理这类失败 |
| [policy-types](../../../packages/experimental/task-strategy/src/policy-types.ts) | 阶段策略同步读取已结算状态；模型请求属于普通任务步骤 | 讨论和裁决需要异步执行路径，不能塞进同步 next 函数 |
| [Superpowers 插件](../../../packages/experimental/task-strategy/src/plugin-superpowers-style.ts) | 挂载 DSH 内的 Superpowers 风格策略 | 黑板流程属于该策略扩展，不代表加载外部 Superpowers skill（技能） |

普通策略子步骤不会因已有 agent-team 服务而自动成为团队成员。接入需要明确任务、成员、会话及后端引用的对应关系，并把能力交给实际使用它的决策会话和执行成员。

<a id="preserving-existing-workflows"></a>

## 保持原有链路的含义

策略原有的规划、执行、检查和恢复顺序由策略拥有。适配器保留既有执行后端，将基础服务连接到它能支持的控制入口；新增通信能力本身不构成更换后端的理由。

DSH 内的 codex-style、claude-style、zcode-style 是风格策略。实际 Codex、Claude 或 ZCode 运行器则拥有自己的会话和执行链路。这两种接入需要分别描述，不能把名称相近当作能力等价。

对于 DSH 风格策略，基础能力支持其在 DSH 中持续协作；这不保证复现外部产品的完整行为。对于实际原生运行器，适配器应列明后端是否支持继续会话、执行中消息、成员控制及状态查询；只返回最终结果的适配器不能据此宣称支持完整协作链路。

某项后端能力不可用时，适配器返回明确的能力限制。它不能悄悄用新会话替代原会话，再声称上下文已经延续。当前设计也不要求其他三个策略采用 Superpowers 的议题、会议或风险模型。

<a id="superpowers-blackboard-workflow"></a>

## Superpowers 黑板流程

黑板围绕问题、已采取的动作、讨论和决策组织共享记录。问题可关联原任务、提出者、影响范围、风险判断、证据和处理进展；决策可关联有关问题、作出决策的会话、采用的方案及受影响成员。字段的具体类型和工具名称留给实现计划，业务关系以本节为准。

1. 执行成员发现计划外问题，并说明事实及影响。
2. 对低风险问题，成员自行决定并执行，将问题、动作和结果提交到黑板。
3. 对中风险或高风险问题，Superpowers 汇总尚待裁决的议题；中风险达到配置数量时发起讨论，高风险采用更小的数量门槛。
4. Superpowers 按配置周期让策略主 agent 查看黑板并作出裁决，也可按议题触发讨论。
5. 讨论结果写入黑板，形成与有关问题关联的决策，并发送给受影响成员。
6. 成员读取相关黑板内容和决策，回报如何调整后续工作；存在疑问时继续沟通。

“成员吸收决策”通过成员回报和后续执行观察，不能由投递成功推断。决策与黑板内容带有版本引用，便于判断成员采用的是哪次调整；具体回报工具由 Superpowers 流程定义。

风险分类、数量门槛、统计范围和裁决周期属于 Superpowers 配置。本文只保留用户提出的相对关系，不选择具体数值，也不增加全局停工或审批规则。开会期间哪些工作继续、哪些工作等待，由后续 Superpowers 流程设计明确。

<a id="unexpected-problems-and-recovery"></a>

## 异常反馈与恢复

成员遇到缺失依赖时，可以报告问题、证据和当前执行状态。Superpowers 将问题加入黑板并组织裁决；其他策略通过自己的恢复流程处理。DSH 负责把调整交给正确成员，并返回继续、重新启动或无法继续的实际结果。

基础设施需要区分成员本轮结束、业务问题待处理、执行失败、任务取消和后端状态不明。策略据此选择动作。某个成员结束并不等于整个任务验收通过；任务完成与产物验证也需要分别表达。

策略接入必须处理当前 TaskRun 的终态规则：可恢复问题应在策略拥有的执行路径中返回给决策流程；已经终止的旧运行不能仅靠追加消息就被当作恢复成功。具体接入方式需要在实现计划中对照运行所有权和取消机制确定。

任务取消后，DSH 清理该任务拥有的活跃执行、等待和周期唤醒。后端执行结果不明时，先报告状态或查询已有执行；恢复能力不应把未知结果自动解释成需要再次执行。

<a id="validation-goals-and-scope"></a>

## 验证目标与范围

后续验证应证明：已有成员能收到调整并继续有关会话；投递结果与成员回报可区分；共享记录可重建且旧版本更新不会覆盖新决策；取消后任务不再唤醒成员；Superpowers 能完成发现问题、记录、讨论、裁决、反馈和继续执行的完整过程。

其他三个策略的验证重点是各自流程和执行后端保持原有选择，且不被注入 Superpowers 的风险门槛或会议规则。原生后端的继续与消息能力要通过各自适配器验证，不能用 DSH 内的测试替代。

本轮范围是能力与职责说明。实现分为基础能力接入和 Superpowers 黑板使用两部分；黑板界面、原生后端全面改造和统一四策略调度不在本说明的实现承诺内。具体协议、默认配置和测试用例将在书面设计审阅后形成实现计划。
